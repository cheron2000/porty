## 4. Implementation standards

Once the owner approves the specification and architecture:

### Repository structure

Choose a structure appropriate to the confirmed stack. Avoid creating empty layers and folders without a concrete purpose. Keep UI, business logic, data access, API clients, and configuration separated where the complexity warrants it.

### Code quality

- Use consistent naming and formatting conventions.
- Enable static analysis and type checking appropriate to the chosen language.
- Keep functions and components cohesive and reasonably small.
- Avoid duplicate logic; extract shared code only when reuse is real.
- Validate untrusted input at system boundaries.
- Use explicit error types and actionable error messages.
- Avoid swallowing exceptions or using broad catch-all handlers without a recovery policy.
- Keep secrets and environment-specific configuration out of source control.
- Provide example environment configuration with placeholder values only.
- Document non-obvious design decisions.

### Frontend requirements (if a frontend is confirmed)

- Use semantic HTML and accessible controls.
- Support keyboard navigation and visible focus.
- Provide loading, empty, error, success, and disabled states.
- Validate forms on both client and server where a backend exists.
- Handle responsive layouts and common viewport sizes.
- Avoid unnecessary client-side state and dependencies.
- Do not expose private API keys or privileged tokens in browser bundles.

### Backend requirements (if a backend is confirmed)

- Define versioned, documented API contracts.
- Validate request bodies, query parameters, and path parameters.
- Enforce authorization on the server; hiding UI controls is not authorization.
- Use parameterized database operations or a safe ORM.
- Apply rate limiting and abuse controls where public endpoints require them.
- Set explicit timeouts for outbound network calls.
- Add structured logs with correlation IDs while excluding secrets and sensitive data.
- Plan migrations, backups, and recovery before storing important user data.

## 5. Security baseline

Perform a threat review appropriate to the product before launch.

At minimum:
- Never commit credentials, private keys, access tokens, or production data.
- Add and verify a suitable `.gitignore`.
- Keep local secrets in environment variables or a secret manager.
- Apply least-privilege permissions to tokens and service accounts.
- Validate and normalize user input.
- Protect against XSS, CSRF, injection, SSRF, insecure direct object references, and broken access control as relevant to the chosen architecture.
- Use HTTPS in deployed environments.
- Set secure cookie/session attributes if cookie authentication is used.
- Avoid logging passwords, tokens, personal data, or full sensitive request bodies.
- Review dependency vulnerabilities and update risky packages.
- Provide a responsible way to report security issues if the product is public.

Do not claim the application is secure merely because these checklist items are documented. Verify implementation and tests.
