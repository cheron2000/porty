## 1. Executive summary

**Verified purpose:** Agent is a Python-based Windows desktop automation framework. Its main execution path observes the user's real interactive Windows desktop, reasons over the visible UI, and dispatches mouse/keyboard input to that same desktop. The project explicitly positions direct-desktop automation as its primary experience.

Main layers:

- **Eyes:** screen capture, OCR, Windows UI Automation (UIA), computer-vision fallback, visual element grounding, observation construction, screenshot lifecycle.
- **AgentHands:** physical mouse, keyboard, window focus, typing profiles, clipboard paste, desktop interaction helpers.
- **DesktopAgentController:** Python facade combining perception, Context, action verification/recovery, and goal execution.
- **Context:** rule-based situational analysis returning a state, explanation, and proposed next action.
- **Action lifecycle:** target resolution, freshness checks, dispatch, post-action observation, verification, bounded recovery.
- **Planner:** multi-step goal plans with dependencies, SQLite checkpointing, recovery, and audit trail.
- **REST interface:** FastAPI service and HTTP client for authenticated local access.

**Assessment:** This is substantially more than a simple click bot. Strong design choices include grounded UI element selection, fresh-observation verification, prevention of automatic retries for non-idempotent actions, and persistent goal checkpoints. Main concerns are unclear boundaries between direct-desktop and Playwright/canvas paths, concurrency around shared desktop state, dependency/install reproducibility, and drift between current code and historical task notes.

## 5. Actual implementation behavior

### 5.1 Perception fusion

Eyes/observe.py builds a structured observation from multiple signals:

1. UIA elements are included first.
2. OCR elements are compared against existing elements using intersection-over-union (IoU). Matching OCR can enrich generic UIA labels; unmatched OCR becomes text elements.
3. CV-detected controls are added when deep mode is requested or the merged set is sparse.
4. Elements are sorted in approximate reading order.
5. The observation carries an ID, active window, screen size, element metadata, image paths, mode, and timing information.

The merge logic prioritizes UIA and uses geometric overlap to avoid duplicates. The Observation schema supports compact serialization and lazy scene-graph construction.

### 5.2 Target grounding

The action orchestrator begins target resolution with semantic scene-graph querying. The graph supports relational queries such as an element inside, next to, above, or below another element. The orchestrator can use the current observation's semantic/UIA/OCR information and fall back to controller visual grounding for icon-only or poorly labelled controls.

Element IDs are tied to observations, not permanent UI identities. Re-observe before acting when the observation is stale or the UI has changed.

### 5.3 Context reasoning

ContextAnalyzer.analyze() accepts an observation object or dictionary. It checks, in order:

1. Dialogs and popups.
2. Chrome profile picker.
3. Supported Instagram workflow states.
4. Chrome tab occupancy/new-tab state.
5. Generic-page fallback.

It returns a ContextReport containing state, situational explanation, user-facing utterance, confidence, active window, and structured ActionRecommendation. This is a deterministic/rule-based engine, not a general learned planner. Do not represent its supported patterns as arbitrary application understanding.

### 5.4 Action lifecycle and safety

ActionOrchestrator documents and implements:

    instruction -> target resolution -> freshness check -> dispatch
                -> post-observe -> verification -> recovery or hard stop

Key rules:

- Dispatch success alone does not prove the application completed the action.
- Verification uses a fresh post-action observation and explicit expectations when available.
- A stale or missing post-observation is classified as uncertain rather than successful.
- Recovery re-resolves targets when observations are stale or elements disappear.
- The recovery decider permits at most one retry for safe repeatable actions by default.
- Non-idempotent actions (for example submit/delete/payment/message-like actions) are not automatically retried.
- Dry-run mode exists for lifecycle testing without physical input.
- Orchestrated steps retain audit records for dispatch, confirmation, evidence, recovery, retries, and latency.

This risk classification is a critical invariant. Never weaken it merely to make automation appear more autonomous.

### 5.5 Multi-step planning and persistence

AutonomousGoalExecutor executes structured plans through the action orchestrator. Its stated design includes dependency ordering, cooperative cancellation, SQLite-backed durable checkpoints, crash reconciliation, and compensatory recovery. checkpoint_store.py creates goal and action-journal tables and configures SQLite WAL mode. The executor can resume a goal from persisted state.

Do not bypass the orchestrator from the goal executor or dispatch raw mouse/keyboard actions directly from a planner step. Keep every atomic action subject to grounding, verification, and risk rules.

### 5.6 Physical input

AgentHands provides the physical input layer. Mouse and keyboard modules call PyAutoGUI, apply coordinate bounds where configured, check for an interactive desktop, and enable the PyAutoGUI corner fail-safe. Keyboard support includes key aliases, hotkeys, and clipboard paste with optional clipboard restoration. The typing engine provides selectable typing profiles.

### 5.7 REST server

agent_server.py creates a FastAPI application on port 8765. It:

- Loads AGENT_AUTH_TOKEN or generates and persists a token in .agent_token.
- Accepts Bearer auth and the X-Agent-Token header.
- Uses constant-time token comparison.
- Checks request Host against localhost/127.0.0.1/testserver plus optional ALLOWED_HOSTS.
- Uses Pydantic request models with bounds and paired-coordinate validation.
- Uses separate locks for Eyes and Hands operations.
- Exposes health, Eyes, Context, and Hands operations.

The documented intended bind address is loopback. Verify the actual Uvicorn host/bind configuration before exposing it to a LAN or public network.

## 9. Evidence-based risks and technical debt

### P0 — resolve before major architecture work

1. **Clarify the two automation surfaces.** The primary docs describe direct Windows desktop control, while a Playwright-backed parallel_desktop_server.py and canvas-oriented planning artifacts are also present. Define which path is supported, experimental, or legacy. Update README, architecture docs, and agent instructions to agree.
2. **Do not trust stale task snapshots as current truth.** .agents/tasks/workspace-analysis.md says parallel_desktop_server.py is missing and describes uncommitted local changes. Current GitHub code search finds parallel_desktop_server.py on the analyzed snapshot, and fetched ai_controller.py imports time and List. Revalidate historical findings against current source before acting.
3. **Desktop automation is consequential.** Maintain explicit user consent, a visible emergency stop, strict target grounding, and non-idempotent retry prevention. Do not add unattended high-impact actions without a permission/risk model.

### P1 — concurrency and state isolation

4. **Shared desktop is a single mutable resource.** The code has locks in the REST server and a module-level re-entrant lock in the goal executor, but direct facade usage and module-level Eyes state need careful audit. Ensure every path that can control the same physical desktop is serialized consistently.
5. **Observation IDs and screenshot sessions are ephemeral.** Avoid caching element IDs across observations or task sessions. Keep screenshot cleanup in task context managers and test exception/cancellation paths.
6. **Multiple interfaces may bypass one another's controls.** Ensure direct controller, REST server, Planner, HumanPlanner, and any Playwright service share a documented concurrency and safety contract.

### P1 — dependency and platform reproducibility

7. **Windows-specific runtime assumptions.** The project requires a real interactive Windows desktop, external Tesseract, and Windows UIA/Win32 packages. Headless CI and disconnected RDP sessions may not exercise actual automation paths.
8. **Dependency declarations are duplicated.** requirements.txt and pyproject.toml both list many dependencies. Establish one canonical dependency source or automated consistency checks. Avoid unpinned drift if stable desktop automation is required.
9. **Packaging boundaries need validation.** pyproject.toml lists root-level modules explicitly and Hands is installed separately in the README. Verify a clean install from a fresh environment and ensure all packages/subpackages are included.

### P2 — maintainability and quality

10. **Bundled skill trees appear duplicated.** Search results show corresponding Eyes/skills/skills and Hands/skills/skills content, including Claude API and web-app-testing skill docs. Confirm whether duplication is intentional; if shared, consider one canonical skill directory with explicit packaging/copy rules.
11. **Historical plans can drift.** Eyes/PLAN.md, .agents/tasks/plan.md, and task JSONs contain older canvas-specific work. Add last-validated commit/date metadata and require source verification before resuming old plans.
12. **Observability should be standardized.** The orchestrator already records action evidence. Correlate REST requests, goal IDs, step IDs, screenshot session IDs, and recovery decisions in structured logs without logging credentials or sensitive screen contents.
13. **Performance budgets are not established in the inspected evidence.** Track capture/UIA/OCR/CV/grounding/verification latency, target accuracy, false-click rate, uncertain-action rate, and recovery success.

### Phase 4 — evaluation and reliability
